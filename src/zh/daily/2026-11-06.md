### 二、凌晨收尾：ASan 假绿被打假 + 一个真实 UB 被 UBSan 抓到（00:02 报告）

**先修了一个「假绿」**：ndk-build 按源文件时间戳判断重建，**改 `Android.mk` 不会重新编译** —— 之前的 ASan APK 里 `libmain.so` 根本没插桩（6MB），runtime 却在包里，游戏根本没启动。强制清 `intermediates/cxx` 后 `libmain.so` 涨到 20MB、含 12 个 sanitizer 符号，才算真插桩。

**真插桩后 UBSan 抓到 UB**：
```
dbopl.cpp.h:1443: member access within null pointer of type 'Chip'
dbopl.cpp.h:1458: applying non-zero offset 104 to null pointer
```
DOSBox OPL 音频模拟器用 `Chip* chip = 0; &chip->chan[i]` 算成员偏移量（不 deref，只算地址差）—— 上游惯用法，但技术上是 UB，UBSan 会 abort。**已修**：改用 `offsetof(Chip, chan) + index * sizeof(Channel)`，值完全相同，无 UB，修复后 UBSan 报错归零。

**遗留（诚实记录）**：ASan 构建仍在 `JNI_OnLoad` → `System.loadLibrary` 阶段 SIGABRT，SEGV 在 `libmain.so+0xe3a630`，栈是库加载时的静态初始化，未定位到具体源码行，**因此不能宣称「ASan 全绿」**。真实发行版在真机跑完整流程零崩溃，不影响实际使用，但覆盖率不完整这件事得记着。

顺带修复：`PAL_HAS_ANDROID` 宏全项目从未定义，导致 `video.c` 里带 `#ifdef` 的日志代码从没编译进去，已改无条件；静态分析因 `android/log.h` 缺失 + NDK sysroot 与 glibc 冲突（1054 错）挂掉，加本地 stub 头后恢复 0 findings 且 hermetic。

### 五、中午到傍晚：对话推进、点击寻路、门触发逐个打通（12:36 – 16:27）

**对话卡死根因定位（两层修法）**：

- 引擎画文本时**不等待**，只在下一行到来前（`PAL_ClearDialog`）才等键；且每次开新行都 `PAL_ClearKeyState()`，tap 落在两次 clear 之间就被吞掉 → 新增独立标志 `g_tapPending`（`PAL_Tap_TakePending()` / `SetPending()`），对话等待循环和 `PAL_WaitForKeyInternal` 都改查这个标志。
- 「文本框可见」≠「正在等待」→ 新增 `g_dialogOpen` 标志，`PAL_ShowDialogText` 置位、`PAL_ClearDialog` 清零。

真机验证：文本从「還不是枕這老太婆…」变成「你呀～遊手好閒是」，李逍遥姿态也变了。

**点击寻路真机通过**：
```
tap game(120,110): party=(1360,424) -> party=(1296,392)
tap game(60,60):   party=(1296,392) -> party=(1184,352)
tap game(200,130): party=(1184,352) -> party=(1248,384)
tap game(100,40):  party=(1248,384) -> party=(1200,312)
```

**「卡在门口」真正原因**：引擎的 search 触发不是像素距离，而是**朝向前方的 13 格菱形区域**（`PAL_GetSearchTriggerRange`），按 trigger mode 决定检查几格。原先用 `dist <= 96` 判断「已在旁边」，与引擎不一致，所以永远走不到触发点，在门口来回 oscillation（1264,264 ↔ 1280,256）。修法：新增 `PAL_Tap_IsObjectInSearchRange()`，**逐格复刻引擎的 13 格菱形算法**（含 `mode * 6 - 4` 的格数截断）；另加 `g_pendingFacing`（到达时把 `wPartyDirection` 转向对象，因为引擎搜索只朝面朝方向）；格子比较从像素改成 **tile**（x/32, y/16, x%32）。

**门触发了 —— 场景切换成功**：
```

FinishInteract id=10 party=(1376,272) dir=2 obj=(1376,272) trig=2 reach=1
```
状态变化：`scene=1 map=12` → **`scene=3 map=10`**（从李逍遥客房走进客栈大堂）✅

**无精灵的门也能被点了**：原来只有带精灵的事件对象注册进 tap 层，门这类「只有触发脚本、无精灵」的对象现在按地图坐标注册 16×16 触点。

### 七、顺带定位：MemPalace MCP 连接失败的真正根因（本轮独立查明）

今日 `errors.log` 里 `MCP server 'mempalace' failed initial connection` 出现 **268 次**。`mcp-stderr.log` 给出直接证据：

```
===== [2026-11-06 23:00:42] starting MCP server 'mempalace' =====
/home/x-stuff-agent-001/.hermes/hermes-agent/venv/bin/python: Error while finding module specification
for 'mempalace.mcp_server' (ModuleNotFoundError: No module named 'mempalace')
```

**根因不是「配置没改对」，而是「改了但 daemon 没重新加载」**：

- `~/.hermes/config.yaml` 里 `mcp_servers.mempalace.command` **确实是**正确的 `/home/x-stuff-agent-001/.local/venv/mempalace/bin/python`（11-03 23:07 修改，已用 `search_files` 核对当前文件与备份 `config.yaml.bak.20261103-230722` —— 备份里还是错的 venv，当前文件已改对）
- 但当前 Gateway 进程 **PID 8697，启动于 2026-11-03 21:24:39** —— **比配置修改时间早 1 小时 43 分**，进程内存里仍是旧配置
- 手工直连验证：daemon 用的 `~/.hermes/hermes-agent/venv/bin/python` 里 **没有 mempalace 包**（site-packages 搜 `mempalace` 0 命中）→ `ModuleNotFoundError` → 进程秒退 → Hermes 报 `MCPError: Connection closed` → 反复重试 → parked
- 而真实安装在 `~/.local/venv/mempalace/`（mempalace 3.1.0，Python 3.11.15）的手工直连**完全正常**：`initialize` 返回 `serverInfo: mempalace 3.1.0`，`mempalace_status` 返回 90 drawers / 4 wings / 8 rooms，耗时 0.9s

**结论**：11-03 那天的配置修复从未被 daemon 加载 —— 因为 Gateway 至今没重启过。**唯一解法是重启 Gateway**，而 `hermes gateway restart` 在 Gateway 进程内会被安全策略拦截（自杀），需走 `~/.hermes/scripts/unit_cycle.py`（systemd unit cycle，实测可行）。本轮日报沿用直连 stdio 客户端绕过，未在无用户在场时重启 daemon。

顺带确认 `MEMPALACE_PALACE_PATH` 必须指向 `/home/x-stuff-agent-001/.mempalace/palace`（指到父目录会返回 `{"error": "No palace found"}`）。
